输入爆了，但不是 Bash 的锅

基于 1,222 条真实蒸馏记录的量化分析。你的假设指向 Bash，数据指向别处。

样本 1,222 jobs DB 1.1 GB 日期 2026-08-19

核心发现 · 假设反转

Bash 平均只占蒸馏输入的 13.6%，在撞预算天花板的输入里只占 2.2%。真正撑爆 256KB 输入的是 thinking 块——在天花板输入里独占 86.8%。砍 Bash 砍不动多少体积，控 thinking 总量才是减容主战场。

预算裁剪砍掉了绝大多数 tool 与 assistant turn（priority=2/3，最先丢），把 thinking（priority=2）+ user（priority=0 永不丢）留了下来。Bash 在天花板输入里只剩 2.2%。

机制：thinking 为什么留到最后

filterTranscriptForDistill 的预算裁剪按 turnPriority 丢 turn：user=priority 0（永不丢）、error-tool=1、assistant/thinking=2、tool=3。超预算时从 priority 高的丢起。thinking 与 assistant 同 priority=2，但 thinking 单条更长、累积更多，于是长会话的 thinking 成了输入的主体。18,872 条 thinking turn 累计 40.7M 字符，平均 2,157 字/条。

结论与建议方向

  • Bash 不是膨胀主因：占 13.6%，输出短（中位 695 字），且几乎不喂记忆（evidence 命中 6.8% 多为命令文本）。砍 Bash 的 cap 收益极小。
  • thinking 是膨胀主因：占 50.8%，天花板输入里 86.8%。但 thinking 是 rationale 载体（origin discipline 放宽后「被采纳的 rationale 可记」），不能简单全删。
  • 预算裁剪方向反了：超预算时把 Bash 等工具结果丢光（p3 先丢），却把大量 thinking（p2）留下——而 thinking 的记忆产出为 0（无 evidence 引用它）。这是高体积零产出的信号。

如果要根治输入爆炸，下一步应在 thinking 总量做 budget 级控制（而非单条 20000 cap），并重新审视 turnPriority——让高产出角色（含命令文本的 user/assistant）优先于零产出的 thinking 块。这是新 brainstorming 的切入点，不是砍 Bash。
